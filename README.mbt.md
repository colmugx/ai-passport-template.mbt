# AI Passport application template

`moon.mod` depends on the published Mooncakes package `colmugx/ai-passport@0.0.6`. Everything the template consumes from the SDK — libraries, the Web Host files, the device Host glue, and the `passport` CLI that builds both Hosts — resolves from that published package through normal Moon dependency resolution (`moon update`); no SDK source checkout is needed anywhere. AI Passport application development is MoonBit application development: a fresh clone needs the MoonBit toolchain and nothing else (the device build additionally needs the ESP-IDF Host toolchain).

## Application contract

The module keeps the normal MoonBit layout (`source = "src"` in `moon.mod`). The application package `src/app` implements the SDK `Application` contract (`update`/`button`/`render`/`audio_output`) and exposes it through `pub fn passport_main()`; that is the entire integration surface. `passport.json` declares that one entry:

```json
{
  "entry": "app"
}
```

The same MoonBit application runs on every supported Host — there are no per-host entries. The Host entry adapters under `src/passport-generated/` are generated by the passport CLI on every build: build output, gitignored, never authored. All Host, runtime, and ABI integration belongs to the SDK, and application code stays independent of browser and device APIs.

## Web development and build

The supported web build command assembles `.passport/web/` (the application wasm, the SDK Web Host files, and the canonical PCM asset under `assets/`):

```sh
moonx colmugx/ai-passport/cmd/passport@0.0.6 build --host web
```

The supported web development command builds that bundle, serves it over localhost, and prints the URL:

```sh
moonx colmugx/ai-passport/cmd/passport@0.0.6 dev
# http://127.0.0.1:8000/index.html?pcm=./assets/forest_walk.pcm&pcmLoop=1
# (append --port 9000 to change the port; Ctrl-C stops)
```

No npm dependencies and no browser tooling are involved. The bundle's only page is the SDK's own `index.html`; the template owns no browser bootstrap JavaScript. ArrowUp/ArrowDown adjust volume and Enter toggles mute (handled by the MoonBit application, the same semantics as the device buttons); click or press a key once to unlock the browser AudioContext.

## Device build

The device backend (the ESP-IDF glue and all hardware bridges) lives in the SDK repository under `hosts/folotoy/ai-passport/`, not in this template. The FoloToy hardware implementation itself is the project-provided dependency pinned as this template's `external/folotoy-ai-passport` submodule, declared to the SDK through `passport.json`'s `hostDependencies`; the SDK does not vendor it.

The device build additionally needs ESP-IDF 5.5.3 (`idf.py` on PATH) plus the MoonBit toolchain; the SDK's `passport doctor --host folotoy-ai-passport` verifies the preconditions.

```sh
moonx colmugx/ai-passport/cmd/passport@0.0.6 build --host folotoy-ai-passport
```

The build materializes the host project into the ignored `.passport/folotoy-ai-passport/` workspace and never flashes. With a board connected, flash and monitor from that workspace:

```sh
.passport/folotoy-ai-passport/flash.sh -p PORT
.passport/folotoy-ai-passport/monitor.sh -p PORT
```

On the board the same application semantics apply: the physical buttons adjust volume up and down and OK toggles mute, and the SDK FoloToy Host runtime applies the hardware-measured 100 ms presentation lead that keeps displayed motion on the audible beat. That lead reaches the application only as the generic `presentation_lead_us` Host fact (the Web Host reports 0); application code never hard-codes device timing.

## Forest Walk

Forest Walk is the default starter and reference application. It is an ambient, fixed-speed scene: the application simulates at a fixed 30 Hz and scrolls at 16.875 logical pixels per second, with no speed or pause controls. The fairy's six-pose walk cycle is beat-locked to the music — one pose per 4/3 eighth notes, spanning exactly one 4/4 bar at the application tempo (114 quarter BPM, i.e. 76 dotted-quarter BPM), with pose 0 on the downbeat. The pose derives statelessly from the audible playback position the Host reports as a generic fact; before audio unlocks, a preview beat clock stands in.

The application ships two committed media artifacts, consumed directly by every build (web, device, CI, fresh clone); nothing regenerates them:

| File | Role |
| --- | --- |
| `src/forest_walk/generated.mbt` | generated runtime data: the six-frame 28×32 fairy sprite sheet, the three 240×160 parallax scenery layers (far, world, foreground) as one small palette plus one-byte pixel indices each, and the canonical audio metadata constants |
| `assets/forest_walk.pcm` | the canonical normalized music: signed PCM16 little-endian, mono, 16000 Hz, headerless (2,444,800 bytes, one 76.4 s loop) |

Both Hosts play the same committed bytes. `passport.json` declares `assets/forest_walk.pcm` as the `pcmLoop` asset.

If you replace Forest Walk with your own application, you choose your own asset authoring pipeline: produce whatever committed runtime files your application loads (MoonBit data and/or media assets declared in `passport.json`) and keep them in your repository. This template owns no authoring tooling.

## Develop

Install the MoonBit toolchain, then run:

```sh
moon update
moon check --target native --output-json
moon test --target native --output-json
moon info
moon fmt
git diff --exit-code
```

The last command checks that API information and formatting are committed. If you create your own application from this GitHub Template, you may rename the MoonBit module in `moon.mod` before publishing it under your own name.
