# ESP32-C3 Forest Walk display firmware

This ESP-IDF 5.5.3 project targets the 8 MB flash, no-PSRAM FoloToy AI Passport ESP32-C3. The T4.0 MoonBit probe, RGB smoke screen and T4.0-B Forest Walk scene were verified on physical hardware. T4.1-A adds the shared-I2C CW2017 battery HUD and flash-resident looping background music. Buttons, Wi-Fi and BLE remain uninitialized.

The required MoonBit toolchain is `moon 0.1.20260904 (94521db 2026-09-04)`. `moonbit-runtime.sha256` pins its distribution's compatible runtime source and headers under `MOON_HOME`. The separate upstream `moonbitlang/moonbit-native-runtime` mirror at revision `7dfc5ca94b4066fff456b0db50fc9d25deeb9cf0` lacks `moonbit_runtime.h` required by this compiler's generated C, so it is not used. Do not substitute runtime sources without updating the compiler and hash manifest together.

The BSP is referenced, never copied: the pinned git submodule at `external/folotoy-ai-passport` (commit `c21a015d44f2bcc02b4d859532d74cd7aefe69be`) provides the display, shared-I2C, CW2017 battery and ES8311 audio sources and headers that `components/folotoy_bsp/` compiles directly from the submodule (see its README for why upstream's own component registration, which would link LVGL and the button stack, is not used as-is; `espressif/esp_codec_dev` is pinned at upstream's 1.6.2). ESP-IDF is pinned to [v5.5.3](https://github.com/espressif/esp-idf/tree/v5.5.3). LVGL is not linked. `bsp_i2c.c` remains the single owner of the I2C0 bus that the battery gauge (0x63) and audio codec (0x18) share.

Source ESP-IDF's `export.sh`, then run `./device/build.sh` from the repository root. The script fails if the SDK environment, Moon version, or runtime hashes differ. It removes stale native capture outputs, invokes `moon build src/device --target native --release` in the root module, and requires a nonempty `generated/moonbit/sources.txt`. During that invocation the script temporarily points the device package's `options.link.native.cc` at `tools/moon_cc_capture.py` through a scratch directory (which also links the real system archiver, so no fake `tools/ar` shim exists) and restores `src/device/moon.pkg` byte-identically afterwards; ordinary host native builds use the standard Moon toolchain. The wrapper records the compiler arguments and copies the generated C. An empty `-o` placeholder is only for Moon's internal build graph; ESP-IDF never reads it. `host_display_stub.c` aborts if a host test unexpectedly calls the device display bridge, and answers `-1` for the battery bridge (no gauge is attached to hosts). Moon may create host scratch objects during its own build, but these remain in ignored `_build/` and are not linked into firmware.

`build.sh` then runs `tools/compile_audio.py`, which converts the single authored `assets/audio/forest_walk.wav` or `.mp3` into `generated/forest_walk.pcm` (raw signed PCM16 little-endian, mono, 16000 Hz — 32,000 bytes per second) with ffmpeg and refuses ambiguous wav+mp3 pairs and over-budget tracks. The PCM is a generated flash asset and is never committed.

`components/moonbit_device` reads the captured-source manifest and compiles the C with the ESP-IDF RISC-V compiler. `components/moonbit_runtime` compiles matching runtime C sources directly. `main/app_main.c` calls `moonbit_runtime_init(0, NULL)`, `moonbit_init()`, then the generated probe and checks for `0xA17E`. It initializes the display and backlight before constructing Forest Walk. MoonBit owns the scene state, logical canvas, draw calls and `DisplaySink`; C owns the monotonic FreeRTOS frame schedule and telemetry, the battery poll and all audio streaming.

`components/battery_bridge` initializes the CW2017 gauge inside its own FreeRTOS task (the first SOC computation can block for seconds, so the frame loop never waits) and then polls state of charge once per second into an atomic cache; every poll is authoritative, storing the fresh 0..100 reading or -1 on failure, so a failed read never leaves a stale percentage in the cache. `ai_passport_battery_soc()` answers 0..100 or -1; the MoonBit device adapter maps anything but 0..100 to `None`, so the HUD shows `--%` when the gauge is missing or unreadable. `components/music_stream` embeds the generated PCM into flash via ELF embedding — there is no heap copy of the track — and one FreeRTOS task streams bounded 240-sample chunks straight from flash-mapped memory through `bsp_audio_write()`, restarting at offset zero on end-of-stream with no allocations. Playback starts at 30% volume; buttons are future work. `ai_passport_music_position_us()` exposes the loop-wrapped write offset (boot-clock fallback while silent) so the MoonBit walk clock can lock the fairy pose to the eighth-note grid; it leads the audible signal by at most the I2S DMA queue (~100 ms).

`components/display_bridge` receives synchronous SDK `FrameView::copy_rgb565_row` output and doubles each logical pixel into a 240×16 RGB565 DMA strip (7,680 bytes). It waits for each `esp_lcd` DMA transfer before reusing the strip. There is no full physical framebuffer. The 40 MHz SPI transfer lower bound for a complete 153,600-byte physical frame is about 30.7 ms, or 32.55 FPS before software and command overhead.

The custom partition table (`partitions.csv`) sizes the factory app at 0x380000 so the ~2.4 MB music PCM fits next to the ~650 KB program image inside the 8 MB flash, leaving ~4.4 MB unused; `sdkconfig.defaults` selects it and `build.sh` verifies the effective sdkconfig keeps `CONFIG_FREERTOS_HZ=1000`, `CONFIG_PARTITION_TABLE_CUSTOM=y` and `CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions.csv"`, demanding regeneration of a stale `sdkconfig` instead of silently assuming them. `tools/compile_audio.py` additionally refuses any PCM above `0x280000` bytes, keeping at least 1 MiB of the partition for the firmware; the ESP-IDF link step remains the final capacity check.

At boot, the firmware logs free, minimum-free and largest internal heap before and after Forest Walk construction, before and after audio initialization, after the first frame, and every five seconds with aggregate `avg_update_us`, `avg_draw_us`, `avg_present_us`, `avg_frame_us`, achieved FPS (scaled by 100), missed frame deadlines and current heap. The loop performs one simulation update per displayed frame and yields after a missed deadline; it does not run catch-up renders. The battery HUD shows the real CW2017 percentage, or `--%` while the gauge is unavailable.

With a board connected, use `./device/flash.sh -p PORT` and `./device/monitor.sh -p PORT`. Check the probe log, far/world/foreground parallax, fairy motion and road alignment, HUD (real battery percentage), continuous looping music at conservative volume, heap trend, five-second frame statistics and absence of resets over at least five minutes. T4.1-A firmware has not yet been validated on physical hardware; battery readings, audio output, heap and frame deadlines must be measured on the board before claiming device stability.
