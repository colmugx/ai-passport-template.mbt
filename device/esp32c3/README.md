# ESP32-C3 Forest Walk display firmware

This ESP-IDF 5.5.3 project targets the 8 MB flash, no-PSRAM FoloToy AI Passport ESP32-C3. The T4.0 MoonBit probe and RGB smoke screen were verified on physical hardware. T4.0-B replaces that scene with the authoritative root `src/forest_walk` package. It does not initialize audio, buttons, I2C, battery, Wi-Fi or BLE.

The required MoonBit toolchain is `moon 0.1.20260904 (94521db 2026-09-04)`. `moonbit-runtime.sha256` pins its distribution's compatible runtime source and headers under `MOON_HOME`. The separate upstream `moonbitlang/moonbit-native-runtime` mirror at revision `7dfc5ca94b4066fff456b0db50fc9d25deeb9cf0` lacks `moonbit_runtime.h` required by this compiler's generated C, so it is not used. Do not substitute runtime sources without updating the compiler and hash manifest together.

The display BSP is the unmodified display subset of [FoloToy/ai-passport at `c21a015d44f2bcc02b4d859532d74cd7aefe69be`](https://github.com/FoloToy/ai-passport/commit/c21a015d44f2bcc02b4d859532d74cd7aefe69be), with its MIT license and pin definitions under `components/folotoy_display/`. ESP-IDF is pinned to [v5.5.3](https://github.com/espressif/esp-idf/tree/v5.5.3). LVGL is not linked.

Source ESP-IDF's `export.sh`, then run `./device/build.sh` from the repository root. The script fails if the SDK environment, Moon version, or runtime hashes differ. It removes stale native capture outputs, invokes `moon build src/device --target native --release` in the root module, and requires a nonempty `generated/moonbit/sources.txt`. `src/device/moon.pkg` configures `options.link.native.cc` to invoke `tools/moon_cc_capture.py`. The wrapper records the compiler arguments and copies the generated C. An empty `-o` placeholder is only for Moon's internal build graph; ESP-IDF never reads it. For ordinary host native tests the wrapper delegates to the host C compiler, and `host_display_stub.c` aborts if a host test unexpectedly calls the device display bridge. Moon may create host scratch objects during its own build, but these remain in ignored `_build/` and are not linked into firmware.

`components/moonbit_device` reads the captured-source manifest and compiles the C with the ESP-IDF RISC-V compiler. `components/moonbit_runtime` compiles matching runtime C sources directly. `main/app_main.c` calls `moonbit_runtime_init(0, NULL)`, `moonbit_init()`, then the generated probe and checks for `0xA17E`. It initializes the display and backlight before constructing Forest Walk. MoonBit owns the scene state, logical canvas, draw calls and `DisplaySink`; C owns the monotonic FreeRTOS frame schedule and telemetry.

`components/display_bridge` receives synchronous SDK `FrameView::copy_rgb565_row` output and doubles each logical pixel into a 240×16 RGB565 DMA strip (7,680 bytes). It waits for each `esp_lcd` DMA transfer before reusing the strip. There is no full physical framebuffer. The 40 MHz SPI transfer lower bound for a complete 153,600-byte physical frame is about 30.7 ms, or 32.55 FPS before software and command overhead.

At boot, the firmware logs free, minimum-free and largest internal heap before and after Forest Walk construction and after the first frame. Every five seconds it logs aggregate `avg_update_us`, `avg_draw_us`, `avg_present_us`, `avg_frame_us`, achieved FPS (scaled by 100), missed frame deadlines and current heap. The loop performs one simulation update per displayed frame and yields after a missed deadline; it does not run catch-up renders. The application renders the semantic unknown battery value `--%`; no device battery percentage is fabricated.

With a board connected, use `./device/flash.sh -p PORT` and `./device/monitor.sh -p PORT`. Check the probe log, far/world/foreground parallax, fairy motion and road alignment, HUD, heap trend, five-second frame statistics and absence of resets over at least five minutes. Physical T4.0-B scene behavior, latency and available heap must be measured on the board before claiming device stability or starting T4.1.
