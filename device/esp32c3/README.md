# ESP32-C3 Forest Walk display firmware

This ESP-IDF 5.5.3 project targets the 8 MB flash, no-PSRAM FoloToy AI Passport ESP32-C3. The T4.0 MoonBit probe, RGB smoke screen and T4.0-B Forest Walk scene were verified on physical hardware. T4.1-A adds the shared-I2C CW2017 battery HUD and flash-resident looping background music (audio playback confirmed on the board); T4.1-B adds the physical volume controls: UP volume+, DOWN volume−, OK mute/unmute. Wi-Fi and BLE remain uninitialized.

The required MoonBit toolchain is `moon 0.1.20260915 (2e1a46d 2026-09-15)`. `moonbit-runtime.sha256` pins its distribution's compatible runtime source and headers under `MOON_HOME`. The separate upstream `moonbitlang/moonbit-native-runtime` mirror at revision `7dfc5ca94b4066fff456b0db50fc9d25deeb9cf0` lacks `moonbit_runtime.h` required by this compiler's generated C, so it is not used. Do not substitute runtime sources without updating the compiler and hash manifest together.

The BSP is referenced, never copied: the pinned git submodule at `external/folotoy-ai-passport` (commit `c21a015d44f2bcc02b4d859532d74cd7aefe69be`) provides the display, shared-I2C, CW2017 battery, ES8311 audio and ADC button sources and headers that `components/folotoy_bsp/` compiles directly from the submodule (see its README for why upstream's own component registration, which would link LVGL, is not used as-is; the managed components are pinned at upstream's versions — `espressif/esp_codec_dev` 1.6.2 and `espressif/button` 4.2.0 — and neither LVGL nor `esp_lvgl_port` enters the build). ESP-IDF is pinned to [v5.5.3](https://github.com/espressif/esp-idf/tree/v5.5.3). LVGL is not linked. `bsp_i2c.c` remains the single owner of the I2C0 bus that the battery gauge (0x63) and audio codec (0x18) share.

Source ESP-IDF's `export.sh`, then run `./device/build.sh` from the repository root. The script fails if the SDK environment, Moon version, or runtime hashes differ. It removes stale native capture outputs, invokes `moon build src/device --target native --release` in the root module, and requires a nonempty `generated/moonbit/sources.txt`. During that invocation the script temporarily points the device package's `options.link.native.cc` at `tools/moon_cc_capture.py` through a scratch directory (which also links the real system archiver, so no fake `tools/ar` shim exists) and restores `src/device/moon.pkg` byte-identically afterwards; ordinary host native builds use the standard Moon toolchain. The wrapper records the compiler arguments and copies the generated C. An empty `-o` placeholder is only for Moon's internal build graph; ESP-IDF never reads it. `host_display_stub.c` aborts if a host test unexpectedly calls the device display bridge, and answers `-1` for the battery bridge (no gauge is attached to hosts). Moon may create host scratch objects during its own build, but these remain in ignored `_build/` and are not linked into firmware.

`build.sh` runs the unified `moon run tools/passport.mbtx assets` step BEFORE the MoonBit C capture: it regenerates the graphics sources and converts the single authored `assets/audio/forest_walk.wav` or `.mp3` into the canonical `.passport/assets/forest_walk.pcm` (raw signed PCM16 little-endian, mono, 16000 Hz — 32,000 bytes per second, exactly one ffmpeg normalization per build) and rewrites `src/forest_walk/generated/audio_meta.mbt`, so the captured MoonBit C can never embed duration metadata older than the embedded PCM. The script refuses ambiguous wav+mp3 pairs and over-budget tracks; the canonical PCM is a generated workspace artifact and is never committed.

`components/moonbit_device` reads the captured-source manifest and compiles the C with the ESP-IDF RISC-V compiler. `components/moonbit_runtime` compiles matching runtime C sources directly. `main/app_main.c` calls `moonbit_runtime_init(0, NULL)`, `moonbit_init()`, then the generated probe and checks for `0xA17E`. It initializes the display and backlight before constructing Forest Walk. MoonBit owns the scene state, logical canvas, draw calls and `DisplaySink`; C owns the monotonic FreeRTOS frame schedule and telemetry, the battery poll, button events and all audio streaming.

`components/battery_bridge` initializes the CW2017 gauge inside its own FreeRTOS task (the first SOC computation can block for seconds, so the frame loop never waits) and then polls state of charge once per second into an atomic cache; every poll is authoritative, storing the fresh 0..100 reading or -1 on failure, so a failed read never leaves a stale percentage in the cache. `ai_passport_battery_soc()` answers 0..100 or -1; the MoonBit device adapter maps anything but 0..100 to `None`, so the HUD shows `--%` when the gauge is unavailable. `components/music_stream` is a pure transport with no control semantics: it embeds the generated PCM into flash via ELF embedding — there is no heap copy of the track — and one FreeRTOS task streams bounded 240-sample chunks straight from flash-mapped memory through `bsp_audio_write()`, restarting at offset zero on end-of-stream with no allocations. `ai_passport_music_position_us()` exposes the loop-wrapped write offset (boot-clock fallback while silent) so the MoonBit walk clock can lock the fairy pose to the eighth-note grid; it leads the audible signal by at most the I2S DMA queue (~100 ms). On hardware the displayed pose still landed after the audible beat (the display pipeline latency exceeds that lead; +150 ms of pose lead overshot into a slight early step), so the device runtime advances the pose position by a measured 100 ms (`FAIRY_POSE_LEAD_US` in `src/device/forest_runtime.mbt`); the browser preview keeps its own audible playback-head timing and is unaffected.

Since R2B, the shared portable `@app.App` is the single owner of the UP/DOWN/OK control semantics (startup volume 80, step 10, clamped to 0..100, remembered mute volume — all tested in `src/app/controls_test.mbt`). `components/button_bridge` owns input delivery only: the BSP ADC button callback (running in the button component's shared timer task) reacts to `BSP_BTN_PRESS` alone and performs nothing but a zero-wait enqueue of a device-neutral button code onto the bridge's own eight-slot event queue; a full queue drops the event into the bridge's own counter, reported as `dropped_button_events=` in the five-second telemetry. The frame task drains at most one event per rendered frame through the MoonBit export `ai_passport_mbt_input_press()` (0 = Up, 1 = Down, 2 = Ok, unknown ignored), which latches exactly one press edge on the shared App. After the App applies the edge, `src/device` mirrors the absolute desired output (`app.volume()`, `app.muted()`) into `ai_passport_music_set_output()` — one packed atomic, latest state wins, no command queue — and the music task applies it to the codec between PCM writes, skipping redundant identical states. The transport is started from the App's own facts (`ai_passport_mbt_audio_volume()` / `ai_passport_mbt_audio_muted()` → `ai_passport_music_start()`), so the App is authoritative before the first PCM sample and no second startup-volume constant exists in C. Muting never stops PCM playback, resets the position or suspends I2S; when music fails to start, presses still reach the App and only the codec output goes nowhere. The former duplicate C volume/mute state machine (`volume_control.h` with its semantic command enum) is removed.

`components/display_bridge` receives synchronous SDK `FrameView::copy_rgb565_row` output and doubles each logical pixel into a 240×16 RGB565 DMA strip (7,680 bytes). It waits for each `esp_lcd` DMA transfer before reusing the strip. There is no full physical framebuffer. The 40 MHz SPI transfer lower bound for a complete 153,600-byte physical frame is about 30.7 ms, or 32.55 FPS before software and command overhead.

The custom partition table (`partitions.csv`) sizes the factory app at 0x380000 so the ~2.4 MB music PCM fits next to the ~650 KB program image inside the 8 MB flash, leaving ~4.4 MB unused; `sdkconfig.defaults` selects it and `build.sh` verifies the effective sdkconfig keeps `CONFIG_FREERTOS_HZ=1000`, `CONFIG_PARTITION_TABLE_CUSTOM=y` and `CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions.csv"`, demanding regeneration of a stale `sdkconfig` instead of silently assuming them. `tools/compile_audio.py` additionally refuses any PCM above `0x280000` bytes, keeping at least 1 MiB of the partition for the firmware; the ESP-IDF link step remains the final capacity check.

At boot, the firmware logs free, minimum-free and largest internal heap before and after Forest Walk construction, before and after audio initialization, after the first frame, and every five seconds with aggregate `avg_update_us`, `avg_draw_us`, `avg_present_us`, `avg_frame_us`, achieved FPS (scaled by 100), missed frame deadlines and current heap. The loop performs one simulation update per displayed frame and yields after a missed deadline; it does not run catch-up renders. The battery HUD shows the real CW2017 percentage, or `--%` while the gauge is unavailable.

With a board connected, use `./device/flash.sh -p PORT` and `./device/monitor.sh -p PORT`. Check the probe log, far/world/foreground parallax, fairy motion and road alignment, HUD (real battery percentage), continuous looping music at conservative volume, UP/DOWN/OK button response (watch for `output volume=… muted=…` transitions starting from the App's 80% and `dropped_button_events=0` in the telemetry), heap trend, five-second frame statistics and absence of resets over at least five minutes. The R2B shared-App control path has not yet been validated on physical hardware; measure it on the board before claiming device stability.
